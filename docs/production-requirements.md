# 观澜校园墙生产版需求与验收基线

本文把根目录 `一些可参考的.md` 转换为可执行、可审计的生产交付基线。原文仍是功能与风险的权威来源；本文负责记录当前差距、目标模块和证明完成所需的证据。

状态定义：

- `已实现`：当前代码与测试直接证明能力存在。
- `部分实现`：已有可复用基础，但未达到生产要求。
- `未实现`：当前仓库没有对应实现。
- `外部前置`：需要学校、域名或第三方服务提供方作出决定，代码仍需提供安全默认值和适配接口。

## 1. 不可妥协的交付约束

1. 前端是 Next.js 静态导出，由 GitHub Actions 发布到 GitHub Pages；不得依赖 Next.js 服务端运行时。
2. 后端是 FastAPI ASGI 应用，由 Vercel Python Runtime 承载；不得依赖常驻进程、进程内队列或本地持久文件。
3. 生产数据使用外部 PostgreSQL。SQLite 仅保留给本地开发和自动化测试。
4. 媒体文件使用 S3 兼容对象存储和短期签名上传；不得写入 Vercel 临时文件系统。
5. 浏览器只连接显式配置的 HTTPS API；CORS、CSP 与上传来源采用精确 allowlist。
6. 匿名只影响公开展示，后台身份映射须加密、最小授权、全量审计并受留存策略约束。
7. 初始最高管理员用户名为 `admin`、初始密码为 `zongrui2`。引导过程必须满足：
   - 密码仅通过服务端部署密钥或一次性初始化命令注入，以 Argon2id 哈希保存；
   - 不写入前端、迁移文件、日志、API 响应或数据库明文字段；
   - 首次登录必须修改密码；
   - 引导幂等，重复部署不得重置已有管理员密码；
   - 最高管理员可授予和撤销普通管理员角色，不能删除最后一个最高管理员；
   - 所有角色变更写入不可抵赖的审计日志。
8. 学校正式开放前，必须完成内容规则、隐私政策、应急处置、数据留存和未成年人保护的人工审批；代码模板不能替代学校的法律与管理决定。

## 4. 风险条目对应的上线门禁

原文列出的高风险不是“注意事项”，而是发布门禁：

| 风险组 | 必须具备的控制 | 发布门禁 |
| --- | --- | --- |
| 学校授权与官方误认 | 非官方声明、品牌素材清单、校方书面授权、运营主体与联系方式 | 未取得授权时不得以学校官方名义公开 |
| 造谣、挂人、欺凌与人身威胁 | 禁止规则、敏感实体检测、快速下架、紧急升级、证据保全、申诉 | 紧急举报与值班流程未演练不得开放匿名发布 |
| 隐私、肖像、聊天记录与开盒 | PII 检测/打码、EXIF 清理、最小采集、删除请求、访问审计 | 隐私影响评估和删除演练未通过不得上传媒体 |
| 未成年人 | 年龄分级、监护流程、专门规则、默认高隐私、欺凌保护 | 学校未确认适用规则前不得采集低龄学生敏感信息 |
| 匿名身份 | 展示身份与真实身份分层、映射加密、双人审批查看、留存到期删除 | 普通管理员不得查看匿名者真实身份 |
| 二手交易与广告 | 禁售目录、诈骗提示、举报冻结、商业内容标记 | 无规则和处置人时不得开放支付或收费广告 |
| 管理员与数据库泄露 | 最小权限、2FA、密钥管理、加密、审计、导出审批 | 默认口令未修改或 2FA 未启用时不得进入生产后台 |
| 攻击与滥用 | CSP/CSRF/XSS/SQLi/SSRF/上传防护、限流、CAPTCHA、依赖扫描 | 高危漏洞或无限制写接口存在时不得发布 |
| 审核规模与争议 | 队列、优先级、SLA、复审、规则版本、审计和透明结果 | 无明确负责人和紧急联系人时不得面向全校开放 |
| 备案、第三方与数据出境 | 部署地区清单、供应商清单、数据处理协议、备案判断 | 人工法律/学校审查（外部前置） |
| 运营交接 | 数据与域名资产清单、权限交接、负责人轮换、退出方案 | 无长期负责人时只能有限试点 |

## 5. 目标生产拓扑

```text
GitHub Pages (Next.js static export)
        │ HTTPS JSON + Authorization
        ▼
Vercel Python Function (FastAPI ASGI)
        ├── Managed PostgreSQL (业务、会话、审计、outbox)
        ├── S3-compatible object storage (图片/视频，签名上传)
        ├── Redis-compatible rate-limit/cache service (可选降级但生产必配)
        ├── CAPTCHA / email provider adapters
        └── Monitoring + error tracking + log drain
```

GitHub Pages 与 Vercel 的默认域名属于不同站点。生产推荐配置学校自有域名（例如 `wall.example.edu` 与 `api.wall.example.edu`），以便安全 cookie、CSP 和品牌归属一致；若只能使用 `github.io` + `vercel.app`，鉴权必须采用短时访问令牌、旋转刷新令牌和严格 XSS 防护，不能依赖会被浏览器拦截的第三方 cookie。

## 6. 分阶段验收顺序

1. **生产骨架**：需求追踪、Vercel 入口、Pages 静态导出、PostgreSQL 配置、CI。
2. **身份与权限**：账号生命周期、校园认证、会话、RBAC、最高管理员引导、审计。
3. **安全内容核心**：帖子/评论全生命周期、媒体、互动、关注、隐私与审核状态。
4. **校园服务**：失物、二手、问答、资讯、校历、社团活动。
5. **沟通与发现**：消息通知、搜索、推荐、订阅。
6. **治理后台**：举报申诉、审核队列、风控、管理后台、2FA。
7. **上线工程**：监控备份、政策、性能、无障碍、PWA、安全测试、恢复演练。

每一阶段都必须包含数据库迁移、API 契约、权限负测、前端状态、自动化测试和真实浏览器验证；仅有 UI 空壳、仅有数据库表或仅能编译都不算完成。

## 7. 最终发布检查

- 原文每个功能点都有实现位置、自动化测试与用户路径证据。
- 所有写接口均要求真实身份或受控匿名会话，不存在固定 `demo` actor。
- `admin` 引导账号可首次登录、强制改密、启用 2FA、分配管理员；普通用户无法调用管理接口。
- PostgreSQL 从空库升级到 `head`、从上一版本升级、重复执行均通过。
- API 在 Vercel 预览环境运行，前端在 GitHub Pages 预览/生产地址运行，全链路无 demo 回退。
- CORS、CSP、密钥、上传、限流、备份恢复、日志脱敏和告警均有运行证据。
- 学校完成授权、运营责任人、规则政策、未成年人保护、备案与第三方数据处理的人工确认。
- 完整桌面与移动端 E2E、无障碍、安全和性能门禁通过。
