# ADR 0002：React、Express 与 PostgreSQL 的生产部署

- 状态：已接受
- 日期：2026-08-24
- 取代：仓库此前的应用运行时与容器部署架构；ADR 0001 中不冲突的构建缓存原则继续有效

## 背景

当前产品由 React/Vite 前端和 Express API 组成，持久数据写入 PostgreSQL 18，上传与派生媒体写入文件系统。生产部署需要一个可重复构建、从空卷自举、可备份恢复且浏览器同域访问的最小拓扑。数据库结构不能继续只依赖应用进程启动时的隐式初始化。

## 决议

1. 使用三个 Compose 服务：`postgres`、`backend`、`frontend`。只有前端 Nginx 对宿主机发布端口。
2. 前后端均使用多阶段镜像。前端最终镜像只含 Nginx 与 Vite 产物；后端最终镜像只含生产依赖、应用代码、迁移工具和媒体处理所需的 `ffmpeg`。
3. Nginx 在同一 Origin 下提供 SPA，将 `/api` 和运行时 `/static` 请求转发给 Express；已有的前端 `/static` 文件优先本地提供。
4. `postgres_data` 持久化 PostgreSQL 18 数据目录，`media_data` 持久化媒体及后端文件型运行状态。运行数据不复制进镜像层。
5. 后端在监听端口前等待数据库，并串行执行带 advisory lock、事务、版本记录和校验和的 SQL migration。迁移只增不改，结构演进采用 expand/migrate/contract。
6. HTTPS 在 Compose 入口之前终止。生产 Cookie 使用 `Secure`，同域默认使用 `SameSite=Lax`，代理必须传递可信的转发协议。
7. 数据库和媒体被视为同一恢复单元；发布破坏性变更前必须生成联合备份。自动化不执行向下迁移。

## 结果

从空卷启动时，健康检查和迁移建立确定的依赖顺序；镜像可替换而不会覆盖业务状态；浏览器不需要跨域 API 配置。代价是部署依赖两个需要协调备份的持久卷，迁移作者必须维护向后兼容窗口。

当前后端存在进程内消息缓存和卷内文件写入，因此本决议只支持单后端副本。未来若需要水平扩展，必须先把共享状态改为具备多写一致性的存储，并另行记录决策。

## 回滚原则

向后兼容的发布可以切回旧应用代码，但后端镜像仍须包含数据库中所有已应用 migration 的完整目录，否则完整性检查会拒绝启动。若数据库已执行不兼容变更，则必须停止写入，同时恢复迁移前的数据库与媒体检查点，再启动对应旧镜像；删除迁移记录或单独回退一类数据不构成有效回滚。
